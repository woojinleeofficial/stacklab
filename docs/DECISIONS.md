# 결정 기록

형식: 결정 · 이유 · 대안 · 되돌리는 방법. 명세(docs/SPEC_v5.5.md)에 없는 선택만 기록한다.

## STEP 0

### D-001 워크스페이스는 단계별로 크레이트를 추가한다
- **결정:** STEP 0에서 `engine`·`solver`·`bot`·`opener`만 만들고 `training`(STEP 2~3), `store`(STEP 2), `app`(STEP 7, 단 화면 골격은 STEP 2부터)은 해당 단계에서 추가한다.
- **이유:** 빈 크레이트를 미리 두면 CI만 늘고 검증할 내용이 없다.
- **대안:** 12.2 구조 전체를 빈 상태로 생성.
- **되돌리기:** `Cargo.toml` members에 추가.

### D-002 좌표계는 y 위쪽 증가, 보드는 행 비트마스크
- **결정:** x는 0~9(왼→오), y는 0이 바닥. 한 행을 `u16` 비트로 저장(40행).
- **이유:** tetris.wiki의 SRS 킥 표가 y-up이라 변환 없이 그대로 쓸 수 있고, 비트 연산이 탐색 속도에 유리하다.
- **대안:** y-down(화면 좌표) — 킥 표를 뒤집어야 해서 실수 위험.
- **되돌리기:** `board.rs`·`piece.rs`에 한정된 변경.

### D-003 킥 표도 룰셋 파일에 둔다
- **결정:** SRS+ JLSTZ·I·180° 킥 전체를 `rulesets/TL-S2.toml`에 넣고 엔진은 읽기만 한다. 엔진 바이너리에는 `include_str!`로 번들한다.
- **이유:** "모든 수치는 설정 파일에서 읽는다"(0장). 새 룰셋 버전 추가 시 코드 변경이 필요 없다.
- **대안:** 킥 표를 코드 상수로.
- **되돌리기:** `ruleset.rs`의 RotationCfg 제거.

### D-004 틱 레이트: 60Hz 프레임 + 프레임당 10 서브프레임
- **결정:** 시뮬레이션 단위는 1/60초 프레임. 입력 이벤트는 서브프레임(1/600초) 타임스탬프를 가진다. DAS/ARR/DCD는 TETR.IO처럼 프레임 단위(소수 1자리)로 설정받아 서브프레임 정수로 저장한다(예: DAS 8.3F → 83 서브프레임). SDF는 배수(5~40, ∞=0으로 표기)로 저장하고 소프트 드롭 속도 = 중력 × SDF(서브프레임 누적, 정수).
- **이유:** TETR.IO가 60fps 기준이며 핸들링 단위가 프레임이다. 서브프레임을 두면 한 프레임 안의 입력 순서를 보존해 리플레이와 피네스 판정이 같은 결과를 낸다.
- **대안:** 순수 60Hz(서브프레임 없음) — 고주사율 입력이 한 프레임에 뭉쳐 순서가 사라진다.
- **되돌리기:** `timing.subframes_per_frame = 1`.

### D-005 소수는 모두 정수 고정소수점
- **결정:** 확률은 ‰(1/1000), 중력은 백만분의 1칸/프레임, 배율은 1/1000. 콤보 ln 공식은 "그 값에 도달하는 최소 콤보" 정수 표로 바꿔 저장.
- **이유:** 결정성(3.2) — 플랫폼별 부동소수점 차이를 원천 차단.
- **되돌리기:** 해당 없음(필수 요건).

### D-006 난수는 Park–Miller 정수 생성기
- **결정:** `seed × 16807 mod (2^31−1)`, 균등 정수는 `floor((x−1)·n/(2^31−2))`로 정수만 사용. 7-Bag은 Fisher–Yates.
- **이유:** 정수만으로 구현 가능하고 결정적이다. TETR.IO와 같은 시드 → 같은 순서 호환은 보장하지 않는다(필요 없음).
- **대안:** xoshiro 등 — 품질은 높지만 차이가 훈련 목적상 의미 없다.
- **되돌리기:** `rng.rs` 교체 + 룰셋/생성기 버전 상승.

### D-007 도달 가능 배치 생성 모델
- **결정:** 좌·우·CW·CCW·180·1칸 낙하·소닉 드롭으로 BFS. 스핀 분류는 "회전으로 바닥에 닿은 상태에 도착"할 때 판정한다. 락 딜레이·리셋 한도는 배치 탐색에서 무시한다(무한 시간 가정).
- **이유:** 솔버·검증기·봇이 같은 이동 모델을 쓴다(3.2). 락 리셋 한도 때문에 실제로는 불가능한 경로가 있을 수 있으므로, STEP 2 검증기는 정답 경로를 **입력 시퀀스로 바꿔 틱 엔진에서 재실행**해 최종 확인한다(5.1 "엔진 재실행 검증").
- **대안:** 탐색에서 락 타이머까지 모델링 — 상태 공간이 크게 늘어난다.
- **되돌리기:** `movegen.rs` 확장.

### D-008 PC 탐색 알고리즘
- **결정:** 높이 제한 DFS + 빈칸 4배수 검사 + 빈 영역별 4배수 검사 + 실패 상태 메모 + 노드 예산. solution-finder(MIT)는 알고리즘만 참고하고 코드는 쓰지 않는다.
- **이유:** 순수 Rust, 외부 의존 없음. STEP 0 측정에서 빈 보드 4줄 PC(큐 11개, Hold)를 전부 찾았다(보고서 참고).
- **대안:** 미리 계산한 PC 패턴 DB — 용량이 크고 문제 생성 다양성이 떨어진다.
- **되돌리기:** `solver/src/pc.rs` 교체.

### D-009 오프너는 "모양 + 분기 그래프"로 정의하고 가시정보 판정은 AND-OR 탐색
- **결정:** 오프너 단계는 목표 모양(채울 칸 집합) + 예약 블록(T 등) + 마무리 조건으로 정의한다. 블록 배정은 고정하지 않고 탐색이 찾는다. `visibleInfoFeasible`은 "보이는 블록(현재 + Next 5 + Hold)과 Bag 카운팅만으로 고르는 전략이 숨은 블록 전부에 대해 성공하는가"를 AND(숨은 블록)–OR(배치) 탐색으로 판정한다.
- **이유:** 8.2의 두 판정을 같은 코드로 증명할 수 있다. Bag 카운팅은 사람이 화면만 보고 할 수 있으므로 공개 정보로 본다.
- **대안:** 블록별 고정 배치표(전통적 오프너 도식) — 미러·순서 변형마다 수작업이 필요하다.
- **되돌리기:** STEP 4에서 분기 그래프 표현을 바꾸면 이 판정 함수만 교체.

### D-010 STEP 0 봇 대결 루프는 블록 단위 시간 근사
- **결정:** 스파이크에서는 봇이 `60000/PPS(milli)` 프레임마다 한 블록을 둔다. 공격표·B2B·Surge·콤보·가비지 이동·상쇄·오프너 페이즈·캡·구멍 규칙은 룰셋 그대로 쓴다.
- **이유:** 강도 조절 손잡이가 단조로운 사다리를 만드는지 먼저 확인하기 위함. STEP 5에서 실제 틱 엔진·입력 실행으로 바꾼다(7.2 "실제 입력 실행").
- **되돌리기:** 해당 없음(STEP 5에서 대체).

### D-011 미확인 룰은 값과 스위치로 분리
- **결정:** 마진 타임 배율은 `margin.enabled`로 켜고 끈다. PC 공격량 등 미확인 값은 `unverified` 주석과 함께 TOML에 둔다.
- **이유:** 12.3 룰셋 출처 규칙.

### D-012 작업 환경
- **결정:** 기본 클라우드 환경이 TETR.IO 문서 사이트를 막아, 이 저장소 전용 개인 환경 `stacklab`을 만들어 문서 호스트 5개(tetrio.github.io, tetris.wiki, tetrio.wiki.gg, harddrop.com, four.lol)만 허용했다(사용자 승인).
- **되돌리기:** 클라우드 환경 설정에서 삭제.

### D-013 Glicko-2는 직접 구현, RD 증가는 TETR.IO 방식
- **결정:** Glickman(2012) 논문 절차를 그대로 구현하고 논문 예제로 테스트한다(14.2). 장기 미사용 시 RD 증가는 TETR.IO와 같이 "7일 유예 후 하루 1씩, 최대 350"을 쓴다(레이팅 불변).
- **이유:** 6.1 "TETR.IO처럼 RD만 서서히 늘리고". 외부 크레이트 의존 회피.
- **대안:** Glicko-2 표준의 기간별 φ* 증가.
- **되돌리기:** `policy.toml`의 `inactivity_*` 값.

### D-014 난이도 앵커는 "고정 시드 + 고정 생성 파라미터" 목록
- **결정:** 앵커 문제는 문제 본문이 아니라 (생성기 버전, 시드, 파라미터)로 고정하고, 생성 결과의 fingerprint를 함께 저장해 생성기 변경을 감지한다. 세부 목록은 `docs/DIFFICULTY_ANCHORS.md`.
- **이유:** 생성기가 결정적이므로 재생성이 가능하고, fingerprint 불일치 시 앵커가 깨졌음을 테스트가 잡는다.

### D-015 PC 공격량 가정
- **결정:** TL-S2 PC = 5줄(별도 공격) + B2B +2로 가정(unverified).
- **이유:** 위키가 10줄은 "outdated"라고 명시하고 QP는 3줄+B2B2. 시즌 2 TL의 정확한 값을 공개 자료에서 찾지 못함. 사용자 확인 대상.
- **되돌리기:** `attack.pc_attack`.

### D-016 저장소 스키마는 STEP 0에서 SQL로 확정하고 STEP 2에서 `store` 크레이트로 옮긴다
- **결정:** `crates/store/migrations/0001_init.sql`. rusqlite(bundled), 마이그레이션은 `PRAGMA user_version` 증가 방식.
- **대안:** ORM(diesel 등) — 오프라인 단일 실행 파일에 비해 무겁다.

### D-017 CI 품질 게이트에서 느린 탐색 테스트는 release 프로필로
- **결정:** CI의 `cargo test`는 `--release`로 돌린다(탐색 테스트가 debug에서 수십 배 느림). `cargo clippy -D warnings`, `cargo fmt --check`는 그대로.

## STEP 0 확인 지점 반영 (2026-11-24, 사용자 답변)

### D-018 PC 공격량 확정
- **결정:** PC는 클리어 자체 공격에 5줄을 더한다(Quad PC 9줄, TSD PC 9줄). 사용자 확인값으로 `user-confirmed` 표시. B2B +2는 계속 unverified.

### D-019 퍼펙트 클리어 범위 확대 (사용자 선호)
- **결정:** 사용자가 PC에 관심이 많아 PC 관련 범위를 넓힌다.
  - D 영역에 사이클당 최소 2문제(`policy.toml` `scheduler.domain_floor.D = 2`). 최대 5문제 규칙은 그대로.
  - D 영역 하위 태그를 넓힘: 2줄 PC, 4줄 PC(빈 보드 1st PC), 2nd PC 이후 연속 PC(10열 7사이클 순환의 각 위치), PC 가능 여부 판단, Hold 경로.
  - 오프너 라이브러리에 PC 계열을 추가: `pco`(+ 2nd PC 연결), `pc-first`(빈 보드 1st PC를 노리는 범용 템플릿 — 암기 대신 솔버 검증된 여러 셋업 중 선택). 주력으로 PCO를 고를 수 있다.
- **이유:** 사용자 요청("퍼펙트 클리어에 로망이 있어서 바운더리가 넓었으면").
- **되돌리기:** policy의 floor 제거, opener 데이터 파일 삭제.

### D-020 와이어프레임은 STEP 0 안 그대로 확정
- **결정:** 사용자가 화면 구성을 위임. `docs/WIREFRAMES.md` 안을 기준으로 STEP 7에서 다듬는다. 사용자가 입문자이므로 UI-03/UI-04 피드백 문구는 용어 설명(툴팁)을 붙인다.

## STEP 1

### D-021 DAS는 누른 서브프레임을 세지 않는다
- **결정:** DAS 10.0F(100 서브프레임)면 누른 시각 + 100 서브프레임에 첫 자동 이동. DCD는 스폰·회전 때 DAS 진행을 그만큼 멈춘다. ARR 0은 벽까지 즉시 이동.
- **이유:** "설정값 ms → 틱" 변환이 피네스 판정과 리플레이에서 같은 값을 내야 함(3.2). 테스트 `das_arr0_reaches_wall`, `arr_repeats_every_arr_subframes`, `dcd_pauses_auto_shift_after_rotation`로 고정.

### D-022 락 딜레이 리셋 모델
- **결정:** 바닥에 닿아 락 타이머가 돌고 있을 때 이동·회전에 성공하면 타이머를 0으로 하고 리셋 횟수 +1(한도 15). 새 최저 행에 도달하면 타이머와 리셋 횟수를 모두 초기화. 공중에서는 타이머 0.
- **이유:** 가이드라인 관례. 세부는 unverified라 `reset_count_restores_on_new_low` 등으로 설정화.

### D-023 가비지 처리 순서
- **결정:** 고정 시 (1) 스핀 판정 (2) 줄 삭제 (3) 공격 계산(마진 배율 적용, 패킷별 내림) (4) 대기 가비지 상쇄(오프너 페이즈면 상쇄력 ×2, 남은 상쇄력 ÷2 올림이 실제 전송) (5) 줄을 지우지 않았으면 이동 시간이 지난 가비지를 블록당 8줄까지 삽입 (6) 다음 블록 스폰(겹치면 Clutch 또는 Block Out).
- 가비지 구멍: 패킷 첫 줄에서 `messiness_between_attacks_pm` 확률로 이전과 다른 열로 변경, 패킷 내부는 `messiness_within_attack_pm`.

### D-024 대전 라우팅과 동시 패배 처리
- **결정:** 두 플레이어를 같은 프레임에 차례로 진행한 뒤 그 프레임의 공격을 서로에게 전달한다(같은 프레임 공격은 다음 프레임부터 상쇄에 쓰임). 같은 프레임에 둘 다 Top Out이면 더 이른 서브프레임이 패배, 같으면 공격량이 적은 쪽, 그래도 같으면 플레이어 2(인덱스 1) 패배. 무승부 없음(7.2).

### D-025 고정 리플레이 파일
- **결정:** `tests/fixtures/replays/`의 리플레이(단일 3개, 대전 1개)를 모든 빌드에서 재생해 최종 상태 해시가 같아야 한다(14.1). 엔진 동작을 **의도적으로** 바꾸면 새 룰셋 버전을 만들거나(배포 후), 배포 전에는 `STACKLAB_BLESS=1`로 다시 만들고 이 파일에 이유를 적는다.
- 2026-11-24: D-021 DAS 수정으로 한 번 재생성(배포 전).

### D-026 정답 경로(witness) 이동 모델
- **결정:** `movegen::find_path`는 좌·우·CW·CCW·180·소닉 드롭만 사용하는 최소 이동 경로를 찾고, `game::path_inputs`가 이를 실제 키 입력으로 바꾼다. 픽스처와 퍼즈 플레이어가 이 경로를 틱 엔진에서 재실행해 같은 배치·스핀이 나오는지 확인한다. 1칸 낙하만으로 가능한 배치는 STEP 2에서 SDF 유한값 입력으로 확장.

### D-027 Rust 툴체인 버전 고정
- **결정:** `rust-toolchain.toml`을 `1.100.0`으로 고정하고 CI도 이 파일을 따른다(`rustup show`).
- **이유:** 첫 CI 실행이 로컬(1.97)보다 새 stable(1.100)의 clippy 린트로 실패. 로컬·CI·Windows가 같은 컴파일러를 써야 품질 게이트 결과가 같다.
- **되돌리기:** 버전을 올릴 때 이 파일과 함께 clippy 수정 커밋.

## STEP 2

### D-028 난수 시드를 splitmix64로 섞는다
- **결정:** `Rng::new(seed)`가 시드를 splitmix64로 섞은 뒤 Park–Miller를 시작한다.
- **이유:** 순수 Park–Miller는 이웃한 시드(1000, 1001, …)의 첫 출력이 거의 같아, 문제 생성기의 매개변수 선택이 한쪽으로 몰렸다(스태킹 9-0 형태 0건). 수정 후 하위 유형이 고르게 나온다(`docs/reports/step2_generation.txt`).
- **영향:** Bag 순서가 바뀌므로 고정 리플레이를 다시 생성(D-025, 배포 전). STEP 0 보고서 수치는 이전 난수 기준의 기록으로 남긴다.

### D-029 피네스 비용 모델
- **결정:** 비용 = 키 누름 수(하드 드롭 포함). 탭과 DAS 홀드는 각각 1. 소프트 드롭 없이 하드 드롭으로 닿는 배치만 피네스 목표로 쓴다. 판정은 비용만 비교하므로 같은 비용의 서로 다른 경로는 모두 정답(테스트 `equal_cost_finesse_paths_are_all_accepted`). 180°는 기본 사용(`allow_180`).
- **난이도:** `1500 + 150×(비용−3) + 80×(180 필요) + 15×지형 높이 + 60×시간 압박 단계`, 시간 압박 단계는 제한시간 정책값 → 10/7/5/3초.

### D-030 스태킹 생성: 조건 먼저, 높이 한도는 증명된 해 이상
- **결정:** 매개변수(블록 수 3~14, 시야 1~5, 시작 높이 2~8, Well 형태, 허용 구멍 0~1)를 격자에서 목표 D에 가장 가깝게 고르고, 지형·블록열을 만든 뒤 빔 탐색(폭 48, 실패 시 160)으로 구멍·Well 조건을 만족하는 해를 찾는다. 높이 한도는 `max(기대 높이, 해의 최종 높이)`로 정해 출제되는 문제는 항상 해가 있다.
- 블록열은 목표 블록 수 + 1개: Hold를 쓰면 마지막에 한 개가 Hold에 남기 때문.

### D-031 검증 = 정답 입력을 틱 엔진에서 재실행
- **결정:** `validator::verify`는 지문(fingerprint) 재계산 → 정답 입력열(witness)을 실제 핸들링으로 틱 엔진에 넣어 목표 달성 확인(피네스는 최소 비용까지) 순서. 실패 후보는 버리고 진단 로그에 남긴다. `ProblemCache.insert`도 검증을 통과한 문제만 받는다.

### D-032 저장소 세부

### D-034 난이도 눈금은 앵커로 고정 (진단 = 앵커 문제)
- **결정:** 영역마다 고정 시드 10개로 만든 앵커 문제(`<영역>:anchor` 구간)를 D=1500 ± 30으로 고정하고 보정하지 않는다. 최초 진단(6.4)은 영역별 앵커 문제로 하고, 이후에도 출제의 15%(`difficulty.anchor_share`)를 앵커로 낸다.
- **이유:** 사용자 레이팅과 문제 난이도를 동시에 보정하면 "차이"만 정해지고 절대 눈금이 떠다닌다. 시뮬레이션에서 앵커 없이 돌리면 정답률은 맞아도 레이팅이 실제 실력에서 200점 넘게 벗어났다(예: 실제 1300 → 1094). 앵커 + 앵커 진단 후 평균 오차 66점.
- **보조 장치:** 사용자 갱신 때 보정 중인 구간 난이도에는 모델 불확실성 150을 RD에 더해 가중을 낮춘다(`MODEL_RD`). 새 구간 초기 RD는 350.

### D-035 75% 목표의 계산
- **결정:** 출제 난이도 중심값은 "흔들기(±120) 평균 정답률이 75%"가 되도록 수치로 구하고, 기대값 계산에 사용자 RD와 구간 RD를 합친 불확실성을 쓴다.
- **이유:** 로지스틱 곡선이 75% 부근에서 오목해서, 단순히 R−191에 ±흔들기를 하면 평균 정답률이 4~5%p 낮아진다.
- **측정 기준:** 14.2의 정답률은 난이도를 맞춘 문제로 잰다. 앵커는 모든 사용자에게 D=1500인 측정용 문제라 목표 75%가 적용되지 않는다(보고서에 별도 표기).

### D-036 새 영역 생성기 방식
- **C 스핀:** 스핀 칸(목표 회전·위치)을 먼저 만들고, 엔진의 판정(종류·Mini/Full·줄 수)이 맞을 때까지 무작위로 받침·지붕을 바꿔 시도. 준비 블록은 완성 보드에서 "맨 위에 놓였을 수 있는" 테트로미노를 전수 열거해 하나씩 떼어내 만든다(역방향 확장). 정답 경로는 그 역순.
- **D PC:** `pc2`는 꽉 찬 2줄에서 블록을 떼어내고 PC 솔버로 순서를 증명. `pc4-n`은 빈 보드에서 n번째 PC 위치(Bag 오프셋)의 블록열로 4줄 PC를 솔버가 증명, `pc4-mid`는 증명된 해를 중간에서 잘라 만든다.
- **F 공격 / G 방어:** 지형·블록열·(대기 가비지)를 정한 뒤 실제 틱 엔진으로 배치를 재생하는 빔 탐색(`GameSim`)으로 최선을 찾고, 목표치는 그 이하에서 요청 난이도에 맞춰 고른다. 가비지 삽입·상쇄·B2B·Surge가 엔진과 정확히 같다.
- **H 판단:** 현재 블록의 모든 배치를 2수 앞까지 평가해 최고점 −8 이내를 모두 정답으로 인정(다중 정답). 최고 대비 탈락 배치와의 차이가 40 미만이거나 정답이 4개 이상이면 비평가용(`rated=false`, MMR 미반영).
- InitialState에 `incoming`(시작 시 대기 가비지)을 추가했다(serde 기본값으로 기존 리플레이 호환).

### D-037 사이클 슬롯과 대체 출제

### D-040 DT Cannon 보류
- **결정:** DT Cannon은 이번 단계에서 넣지 않는다.
- **이유:** 위키 도식이 2Bag에 걸친 모양이고, 회색 칸(다른 Bag/임의 블록)의 의미가 표마다 달라 칸 수가 4의 배수로 맞지 않았다. 출처로 확인되지 않은 도식을 추측해 넣으면 "검증된 문제만 출제" 원칙을 어긴다.
- **대안:** 사용자가 쓰는 DT Cannon fumen(또는 four.lol 등 다른 출처)을 받으면 `tools/fumen_decode.py`로 옮겨 넣는다. 데이터 파일 하나 추가로 끝나며 코드 변경은 필요 없다.
- **명세 영향:** 8.3 초기 라이브러리 4종 중 DT Cannon이 빠지고, 사용자 선호(D-019)에 따라 `pc-first` 템플릿이 들어갔다.

### D-041 실행 가능성 판정의 계산 방식
- **결정:** 암기형 분기는 "블록별 목표 칸"이 정해져 있으므로 순서 문제로 푼다: 상태 = (놓은 블록 집합, 큐 위치, Hold), 각 블록은 그 시점에 도달 가능할 때만 놓을 수 있고 분기에 없는 블록은 Hold에만 둘 수 있다. 예약 블록(TKI의 T)은 완성 시점에 쓸 수 있어야 한다. 가시정보 판정은 같은 상태에 "공개 블록 열"을 더한 AND-OR 탐색. 분기가 여럿이면 "시작 시 한 분기에 맡기는 전략"으로 보수적으로 판정한다.
- **결과:** 첫 Bag 5,040가지 전수 — TKI 69.0%, PCO 85.2%(Hold, Next 5). 첫 Bag 7개는 Next 5 + Bag 카운팅으로 모두 알 수 있으므로 가시정보 = 전체순서 결과가 같다. 계산 결과는 `data/openers/coverage.toml`에 저장(앱이 실행 중 재계산하지 않음, 버전 불일치는 테스트가 잡음).
- **템플릿:** `free-transition`은 빔 탐색으로 7블록 뒤 구멍 0·높이 6 이하 도달 여부, `pc-first`는 PC 솔버(다음 Bag이 필요하므로 가시정보는 다음 Bag 표본 4개로 "추정"이라 표시). 템플릿은 표본 범위라 '100% 가능'을 표시하지 않는다.

### D-042 오프너 문제(E)
- **결정:** 역할 비율은 정책값(주력 70 / 전환 판단 20 / 예외 10). 주력 문제 = 보이는 블록으로 주력이 가능한 큐, 정답 = 그 큐로 만들 수 있는 주력 분기 전부(다중 정답) + 분기에 마무리가 있으면 이어서 T-Spin. 전환 문제 = 주력이 불가능하고 예외가 가능한 큐, 정답 = 예외(주력을 쌓으면 실패). 예외가 템플릿이면 목표는 스태킹 조건(자유 전환) 또는 PC(pc-first).
- 숙련 MMR은 오프너별(역할과 무관), 분기 통계는 `오프너/분기`별. 로드아웃 변경은 이 기록을 건드리지 않는다(테스트로 고정). E는 로드아웃이 있을 때만 출제되고 앵커 비율에서 제외한다(오프너 문제의 눈금은 STEP 5 실전 관측과 함께 보정).

### D-046 봇 리그 등급 계산: Bradley–Terry 최대우도
- **결정:** 리그 등급은 Glicko-2와 같은 로지스틱 눈금(기대 승률 = 1/(1+e^(−Δ/173.7178)))에서 Bradley–Terry 최대우도로 맞추고(MM 반복), 기준 프리셋을 1500으로 고정한다. RD = 173.7178/√(Fisher 정보량). 쌍마다 0.5승을 양쪽에 더해 전승 쌍도 유한값이 되게 한다.
- **이유:** 처음엔 "Glicko-2 한 기간 갱신을 고정점까지 반복"했는데, 96% 승률 쌍(1차 리그의 L2→L3)에서 발산했다(`docs/reports/step5_bot_league_run1.txt`). Glicko-2 갱신은 사전값 근처의 1차 근사라 큰 격차를 한 번에 맞추지 못한다. 최대우도는 같은 모형의 정확한 해다.
- **명세 대응:** 7.3 "Glicko-2로 botRating ± RD 산출" → 같은 눈금·같은 승률 모형의 R ± RD로 산출(사용 중 보정은 Glicko-2 갱신을 그대로 사용, D-048).

### D-047 프리셋 간격 조정
- **결정:** 1차 리그에서 L2→L3 승률이 96%(약 550점 차)라 그 사이에 중간 프리셋(PPS 1.25, 깊이 1, 빔 3, 실수 5%)을 넣고 이후 번호를 하나씩 밀었다. 기준 프리셋은 L4(구 L3).
- **이유:** 7.2의 "예상 승률 40~60%" 상대가 있으려면 인접 프리셋 간격이 대략 200점 안쪽이어야 한다.

### D-048 실전 MMR·TL 앵커·사용 중 보정
- 실전 MMR은 평가전 1세트(무효 라운드 제외)를 한 레이팅 기간으로 Glicko-2 갱신. 미니 대결은 변화 없음.
- TL 앵커: 처음 입력하면(평가전 전) 실전 MMR = 입력 Glicko, RD = max(입력 RD, 150). 이후 입력은 정밀도 가중으로 현재 값과 합치고, 같은 보정량만큼 봇 눈금 오프셋도 이동. 입력마다 (Glicko, RD, 시각, 입력 당시 앱 점수, 그때의 오프셋)을 모두 보존. 앵커가 있으면 평가전마다 오프셋도 학습(봇 묶음을 한 선수로 보고 Glicko-2 갱신, RD 하한 40).
- 표시: 앵커가 있으면 "TL Glicko 환산 추정치 R ± RD", 없으면 "앱 기준 R ± RD". TR·랭크 문자는 계산하지 않는다(6.3).
- 사용 중 보정(7.3-4): 평가전마다 상대 봇 등급을 사용자 결과로 Glicko-2 갱신하되 RD 하한(`match.bot_rd_floor` 50)으로 천천히 움직이고, 경기 기록의 calibrationVersion = 리그 버전 × 1000 + 조정 횟수.

### D-049 엔진 관측 약점의 기준
- 라운드 패배만으로는 약점으로 보지 않는다(7.4). 엔진 통계로만 판정: 블록당 공격 < 0.25(20블록 이상) → F, 가비지 8줄 이상 받고 Top Out → G, 30블록 이상 동안 스핀 0회 → C, 첫 14블록 안에 로드아웃의 오프너 분기 미완성 → E. 각 약점은 해당 영역 출제 가중치에 +0.25(사이클마다 절반으로 감소, 최대 1.8배 상한 유지).

### D-050 세트 상태 머신
- `DIAGNOSIS → TRAINING_1 → MINI_1 → TRAINING_2 → MINI_2 → TRAINING_3 → EVALUATION → RESULT → TRAINING_1`. 미니는 건너뛰기/나중에(평가 결과 전까지 언제든 진행 가능), 평가전은 연기/평가 없이 종료. BO3는 무효가 아닌 라운드 기준 먼저 2승. 정상 완료 여부(`evaluation_completed`)는 STEP 6 추천 트리거가 쓴다.
- 앱 단계 표시는 이 상태를 그대로 따른다. 대결 화면의 봇 결정은 현재 UI 스레드에서 블록마다 한 번(수 ms) 계산한다. 입력·탐색 분리와 지연 측정은 STEP 7(14.4).

### D-051 난수 함수 오버플로 수정
- `Rng::below(n)`의 곱셈을 128비트로 바꿨다. 큰 n(시드 생성)에서 디버그 빌드는 중단, 릴리스는 값이 틀어지던 버그. 작은 n에서는 결과가 같아 기존 리플레이·생성 결과는 바뀌지 않는다(고정 리플레이 테스트 통과).

## STEP 6

### D-052 조합 적합도 계산
- **사용자 능력 벡터:** 기술 MMR을 0~100으로 환산(1000 → 0, 2000 → 100, 표준편차 = RD/10). 차원 = 피네스(A)·스태킹(B)·스핀(C)·PC(D)·암기(E)·공격(F)·방어(G)·판단(H). 오프너 요구 벡터·특성값은 라이브러리 데이터.
- **조합 단위 평가:** 능력 적합·관측 성과·공격/후속·학습 부담은 "주력이 가능한 Bag 비율 c_p × 주력 값 + (1−c_p) × 예외 값"으로 합친다(주력이 커버하는 상황 + 주력 불가 시 예외가 보완하는 상황, 9.2).
- **상호 보완(20):** 주력 또는 예외가 가능한 첫 Bag 비율. 두 오프너가 모두 전수 범위면 Bag별 비트셋(`coverage.toml`의 `bits`)으로 정확히 계산, 템플릿(표본)이 섞이면 독립 가정 + 표본 구간을 불확실성으로 반영(모델 추정값 표시).
- **관측 성과(25):** 오프너 숙련 MMR(1000 → 0, 2000 → 1)과 실전 관측 성공률(2라운드 이상일 때 30%)을 섞는다. 한 번도 관측하지 않은 오프너는 "능력 적합 × 0.8"을 모델 추정값으로 쓰고 불확실성을 크게(25점 만점의 ±25%) 둔다.
- **80% 구간:** 각 항목 표준편차의 제곱합 + 모델 하한 2점 → ±1.2816σ.
- **변경 조건:** 추천 조합이 현재보다 8점 이상 높고, 추천 구간 하한 > 현재 구간 상한(9.2). 아니면 NO_CHANGE. 로드아웃이 없거나 오프너 유효 시도가 최소치 미만이면 UNAVAILABLE(근거 없는 추천을 만들지 않음).

### D-053 추천 이벤트와 저장
- 자동 이벤트는 "정상 완료된 BO3 + 오프너 유효 시도 10회 + 오프너 관측 라운드 4회(미니 포함)"를 처음 충족한 평가전 직후 1회. 연기·평가 없이 종료·미완료 평가전은 트리거가 아님. DB 부분 유일 인덱스로 자동 이벤트는 최대 1개(9.3).
- 상태 머신은 명세 9.3의 간선만 허용하고 DB 저장 때도 검사. 수동 재분석(UI-07)은 자동 이벤트와 별개로 몇 번이든 가능.
- 적용(9.4)은 한 트랜잭션: 이벤트 상태(READY/DEFERRED) 확인 → 로드아웃 버전 확인(다르면 Conflict, 새 승인 필요) → 조합 유효성 → 변경 이력(approval_event_id 유일) → 로드아웃 → APPLIED. 같은 이벤트를 다시 적용하면 AlreadyApplied(변경 1회). 중간 실패는 전부 롤백.
- 스키마 3: 추천 테이블에 분석 결과(JSON)와 갱신 시각을 추가하고, 트리거 참조를 세트 ID 문자열로 바꿨다(경기 기록 행은 아직 없음 — STEP 7에서 Match/Round 저장 시 연결).

### D-054 UI-08 흐름
- 결과 화면(UI-06)과 오프너 관리(UI-07)에서 진입. 1단계: 현재/추천 조합의 적합도·구간·항목·근거(모델 추정값 표시) + 추천 적용 / 현재 유지 / 나중에 결정. 2단계: 변경 전후와 "기존 숙련도 보존" 안내 + 변경 확정 / 취소. 자동 팝업은 없다(DEFERRED는 UI-07에서 다시 열기).
