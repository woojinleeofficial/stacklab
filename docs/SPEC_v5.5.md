# 0. 이 문서를 읽는 구현 에이전트에게

이 문서는 **Claude Opus 5.5가 처음부터 끝까지 직접 구현하는 것**을 전제로 쓴 구현 지시서다. 사람 외주용 계약·견적 조항은 없다. 읽는 순서와 작업 방식은 다음과 같다.

1.  **12장(작업 방식)과 13장(단계별 구현)을 먼저 읽는다.** 기술 스택, 저장소 구조, 단계별 완료 조건이 여기에 있다.
2.  **명시된 값은 그대로 쓰고, 모호한 부분은 스스로 정한다.** 사용자에게 묻지 말고 가장 합리적인 선택을 한 뒤 `docs/DECISIONS.md`에 근거와 함께 기록한다. 예외는 12.4의 사용자 확인 지점 두 곳뿐이다.
3.  **모든 수치는 설정 파일에서 읽는다.** 16장의 기본값을 `config/policy.toml`과 `rulesets/TL-S2.toml`에 넣고 코드에 하드코딩하지 않는다.
4.  **테스트가 완료 기준이다.** 각 단계는 14장의 해당 체크리스트를 자동 테스트로 통과해야 끝난다.

**개정 이력:** v5.0 초안 → v5.1 기준점·수치 보강 → v5.2 TETRA LEAGUE 시즌 2 룰셋 확정 → v5.3 무승부 제거, Glicko-2 점수 체계, TL 앵커 → v5.4 구현 에이전트용으로 재구성(사이클 단위 갱신, 예상 승률 기반 매칭, 추천 신뢰도 기준 수치화, 기술 스택·작업 규칙 확정, 계약 조항 삭제) → **v5.5 빌드·검증 환경(12.5) 추가, 문서·제품 명칭에서 타사 상표 제거**.

# 1. 제품 요구사항

## 1.1 제품 목표

사용자의 약점을 엔진 이벤트로 정확히 진단하고, 그 약점에 맞춘 검증된 문제와 AI 대결로 실력을 꾸준히 끌어올리는 **1인용 오프라인 훈련 프로그램**을 만든다. 핵심 구성은 다음 다섯 가지다.

-   **공통 엔진:** 문제 풀이, AI 대결, 정답 검증, 리플레이가 하나의 결정적 엔진을 공유
-   **적응형 문제 훈련:** 8개 기술 영역, 자동 생성·검증 문제, 기술별 MMR과 가중치 출제
-   **실전 스파링:** 12문제 × 3사이클 사이에 미니 대결 2회와 BO3 평가전
-   **오프너 시스템:** 사용자가 고른 주력 1개 + 예외 1개를 중심으로 분기 훈련, 숙련 기록 영구 보존
-   **1회 오프너 추천:** 충분한 데이터가 모인 첫 평가전 뒤 조합 추천, 사용자 2단계 승인 시에만 적용

## 1.2 전체 사용자 흐름

`첫 실행 → 키 설정 → 주력/예외 오프너 선택 → 진단 → 12문제 → 미니 대결 → 12문제 → 미니 대결 → 12문제 → BO3 평가전 → 결과·실전 MMR → (조건 충족 시 최초 1회) 오프너 추천 → 다음 세트`

**세트 소요 시간 목표:** 1사이클(12문제) 15~20분, 1세트(36문제 + 미니 2회 + BO3) 약 60~80분. 사용자는 사이클 단위로 중단·재개할 수 있다.

# 3. 게임 엔진 및 룰셋

## 3.1 기준 룰셋: TETRA LEAGUE (랭크 1v1)

모든 엔진 판정, 문제, AI 대결, 오프너 검증은 **TETR.IO TETRA LEAGUE 시즌 2 규칙**을 기준으로 한다. `rulesetVersion`의 기본값은 `TL-S2`이며, 세부 수치는 STEP 0에서 공개 자료로 확정해 설정 파일에 고정한다.

| 항목 | 기준 |
|--------|--------------------------|
| 필드 | 10열 × 40행(표시 20행 + 숨김 영역) |
| 블록·미리보기 | 7종 테트로미노, 7-Bag, Next 5개, Hold(블록당 1회), Ghost |
| 회전 | **SRS+** 킥 테이블 + TETR.IO 고유 180° 킥 |
| 스핀 판정 | **All-Mini+**: T는 T-Spin/Mini 판정(고정 위치 판정 포함), T 이외 블록의 제자리 스핀은 Mini로 인정 |
| B2B | **B2B 차징**: 어려운 클리어(Quad·스핀) 연속 시 공격 추가, B2B 4 이상부터 **Surge** 충전, 연속이 끊기면 충전량을 나눠 일괄 전송 |
| 콤보 | TETR.IO 멀티플라이어 콤보(기본 공격 × 콤보 배율, 내림) |
| 오프너 페이즈 | 경기 시작 후 첫 14블록 동안 가비지 상쇄량 강화 |
| 가비지 | change-on-attack 구멍 배치, 대기·상쇄·적용 타이밍, 패스스루 없음 |
| 패배 판정 | Top Out 규칙 + **Clutch Clear**(블록 아웃 순간 줄을 지우면 생존) |

**STEP 0에서 수집·확정할 수치:** 클리어 종류별 공격표, Surge 시작값·증가량·분할 전송 방식, PC(All Clear) 공격량과 B2B 효과, 오프너 페이즈 상쇄 배율, 가비지 캡·대기 시간·구멍 변경 확률, 중력·락 딜레이, 경기 시간에 따른 공격 배율 변화. 각 수치는 [TETR.IO 메커니즘 FAQ](https://tetrio.github.io/faq/mechanics.html), 공식 패치 노트 등 공개 자료로 확정하고(12.3 룰셋 출처 규칙), 고정 입력·기대 결과 테스트 픽스처를 만든다.

**조작·인터페이스:** 좌/우, Soft/Hard Drop, CW/CCW/180° 회전, 일시정지/재시작. DAS/ARR/SDF/DCD는 TETR.IO와 같은 단위·범위로 설정하고 키 중복 할당을 검증한다.

**룰셋 업데이트:** TETR.IO가 랭크 규칙을 바꾸면 기존 `TL-S2`는 그대로 두고 새 룰셋 버전을 추가한다. 과거 기록은 당시 룰셋 버전으로 재생·해석한다.

## 3.2 결정성과 재현성

-   시뮬레이션은 렌더링과 분리된 **고정 틱**으로 돌고, **정수 연산만** 사용한다. 틱 레이트는 STEP 0에서 확정한다(권장: 60Hz + 입력 이벤트의 틱 내 타임스탬프 보존).
-   DAS/ARR/SDF 설정값(ms)을 틱으로 바꾸는 규칙을 명시해 피네스 판정과 리플레이가 같은 결과를 내게 한다.
-   `초기 상태 + rulesetVersion + 시드 + 입력 이벤트 로그 = 항상 같은 결과`
-   문제 풀이, AI 대결, 정답 검증기는 **같은 엔진**을 사용한다.
-   인터페이스: `reset(seed, ruleset)`, `step(inputs)`, `snapshot()`, `restore()`, `events()`, `replay(log)`

## 3.3 엔진 이벤트

`PIECE_SPAWN`, `PIECE_LOCK`, `LINE_CLEAR`, `SPIN`, `PERFECT_CLEAR`, `B2B_CHANGE`, `SURGE_CHARGE`, `SURGE_RELEASE`, `OPENER_PHASE_END`, `CLUTCH_CLEAR`, `COMBO_CHANGE`, `ATTACK_SENT`, `ATTACK_CANCELLED`, `GARBAGE_RECEIVED`, `HOLD_USED`, `TOP_OUT`, `MATCH_END`를 기록한다. 각 이벤트에는 틱, 상태 참조, 룰셋 버전을 담는다.

# 4. 훈련 콘텐츠: 8개 영역

모든 문제는 `목표 → 시작 상태 → 사용자 행동 → 엔진 이벤트 판정 → 피드백` 구조다. 8개 영역은 12문제 사이클에 가중치로 편성하며, 매 사이클 모든 영역을 강제하지 않는다.

| 영역 | 하위 기술 | 성공 판정 | 난이도 요인 |
|------|------------|--------------|-----------|
| A. 피네스·속도 | 최소 입력, 정확한 배치, 반응 | 목표 위치·회전 일치 + 최소 입력 비용 별도 판정 | 회전·열·입력 설정·시간 |
| B. 스태킹·Hold | 9-0/6-3/7-2/자유형, 지형·Next·Hold | 지정 블록열 동안 구멍·Well·생존 등 명시 목표 충족 | 블록 수·시야·필드 높이 |
| C. 스핀 | T-Spin Single/Double/Triple/Mini, All-Mini+ 올스핀(S·Z·L·J·I·O), 세팅·분기 | 엔진이 판정한 스핀 종류·제거 줄 수 일치 | 준비 블록·회전 진입·분기 |
| D. 퍼펙트 클리어 | 기본 PC, Hold 경로, 연속 PC, 가능 여부 판단 | 숨김 행 포함 전체 필드가 비었음을 엔진에서 확인 | 블록 순서·가능 경로 수·시간 |
| E. 오프너 | 주력·예외 전개, 분기, 오프너 페이즈(첫 14블록) 활용, 중반 전환 | 등록된 유효 분기 완성 또는 정의된 전환 목표 달성 | Bag 순서·전환·시간·정확도 |
| F. 공격 | Quad, 콤보, B2B 차징 유지, Surge 충전·해제 타이밍, 공격 효율 | 룰셋 공격 이벤트·콤보/B2B·Surge 목표 달성 | 공격량·연속성·안정성 |
| G. 방어·복구 | 다운스태킹, 가비지 상쇄, Surge 대응, Clutch Clear 생존 | 가비지 지형에서 복구·상쇄·생존 목표 달성 | 깊이·구멍·대기 공격 |
| H. 순간 판단 | 배치 선택, 전환, 위험도, 타이밍 | 다중 정답 인정, 신뢰도 낮으면 비평가용 | 제한시간·탐색 깊이·가시 정보 |

## 4.1 판정 원칙

-   **피네스:** 키 누름과 DAS/ARR 자동 반복을 구분해 사용자 설정 기준의 최단 비용 경로와 비교한다. 비용이 같은 경로는 모두 정답이다. 배치 성공과 피네스 성공은 따로 저장한다.
-   **스태킹·공격·판단:** 하나의 정답 배치 대신 목표 조건과 엔진 이벤트로 판정하고, 평가 함수의 불확실성은 피드백에 표시한다.
-   **스핀·PC:** 실제 엔진 판정 이벤트로만 성공 처리한다.
-   **힌트·되감기·정답 보기:** 자유롭게 쓸 수 있다. 사용한 시도는 사이클 문제 수에 포함하고, 기술 MMR 갱신에서는 제외한다.
-   **제한시간:** 영역·난이도별 제한시간은 STEP 0 정책 테이블로 확정하고, 1사이클 목표 소요 시간(15~20분)에 맞춰 보정한다.
-   **40라인:** 별도 측정 모드. PPS·완료 시간·입력 통계를 저장하며 사이클과 무관하다.

# 5. 문제 생성 및 검증

## 5.1 파이프라인

`기술·하위 태그 선정 → 목표 난이도 → 초기 상태·블록열 생성 → 룰셋 유효성 → 해결 경로 탐색 → 엔진 재실행 검증 → 난이도 추정 → 중복 검사 → 출제`

`ProblemGenerator`는 후보를 만들고, `ProblemValidator`는 해결 가능성을 증명하고, `DifficultyEstimator`는 난이도를 추정하고, `Scheduler`는 출제 대상을 정한다.

## 5.2 유형별 생성 전략

-   **피네스:** 도달 가능한 목표 위치를 샘플링하고 입력 상태 그래프의 최단 비용으로 정답 비용을 산정한다.
-   **스태킹·다운스태킹:** 조건과 블록열을 먼저 정하고 시드 기반 탐색으로 달성 경로를 확보한다.
-   **스핀:** 정답 스핀 상황을 먼저 만들고 준비 지형을 확장한 뒤 엔진 재실행으로 증명한다.
-   **PC:** 빈 필드 복귀 경로를 먼저 구성하거나 제약 탐색으로 풀이를 증명한다.
-   **오프너:** 검증된 오프너 분기 라이브러리에서 성립하는 Bag 순서와 분기를 생성한다.
-   **공격·판단:** 제한된 탐색으로 다중 정답을 산출하고, 신뢰도가 낮으면 비평가용으로 분류한다.

**기존 오픈소스 활용:** PC 풀이 검증(예: solution-finder), AI 탐색(예: Cold Clear 계열) 등 검증된 오픈소스의 활용·참고를 허용한다. 라이선스는 12.3 작업 규칙을 따른다.

## 5.3 품질과 장애 처리

-   **출제되는 문제는 100% 검증된 문제다.** 검증에 실패한 후보는 버린다.
-   생성이 시간 초과되면 미리 검증한 캐시에서 같은 영역·근접 난이도 문제를 낸다. 캐시도 없으면 다른 영역을 출제하고 진단 로그를 남긴다.
-   최근 5문제와 상태·목표·블록열이 완전히 같은 문제는 내지 않는다.
-   문제마다 `seed`, `rulesetVersion`, `generatorVersion`, `goal`, `solutionWitness`, `difficulty`, `fingerprint`, `subtypeTags`를 저장한다.
-   판정 버그가 확인되면 해당 시도를 무효화하고, 그로 인한 MMR·가중치 변화를 되돌린다.

# 6. 기술별 MMR과 출제 가중치

## 6.1 점수 체계: TETR.IO와 같은 Glicko-2

모든 점수는 TETRA LEAGUE와 같은 **Glicko-2** 방식으로 관리한다. 점수마다 **레이팅(R) ± RD(불확실성)**를 함께 저장·표시하며, 시도가 쌓일수록 RD가 줄어드는 구조가 그대로 "임시 점수" 표시 기준이 된다.

| 점수 | 대상 | 갱신 시점 | 초기값 |
|------------------|--------------|------------|------------|
| 기술 MMR `skillRating[module]` | 8개 영역 각각 | 사이클(12문제) 종료 시 일괄 | 1500 ± 350 |
| 오프너 숙련 MMR `openerRating[id]` | 오프너별 실행 능력(역할과 독립) | 사이클 종료 시 일괄 | 1500 ± 350 |
| 실전 MMR `matchRating` | AI 상대 실전 실력 | BO3 평가전 종료 시 일괄 | 1500 ± 350, 또는 6.3의 TL 앵커 |

-   공통 파라미터(초기값): 변동성 σ=0.06, 시스템 상수 τ=0.5. 오래 쓰지 않은 점수는 TETR.IO처럼 RD만 서서히 늘리고 레이팅은 유지한다.
-   **레이팅 기간:** Glicko-2는 여러 결과를 묶어 한 번에 갱신할 때 가장 안정적이다. 기술·오프너 점수는 **1사이클(12문제)**, 실전 점수는 **평가전 1세트**를 한 레이팅 기간으로 묶어 갱신한다. 사이클 도중 화면에는 직전 확정값과 '진행 중 추정치'를 함께 보여준다.
-   RD가 100을 넘는 점수는 "임시"로 표시한다.
-   세 점수는 서로 대체하지 않는다.

## 6.2 문제 난이도 척도와 자동 보정

문제 난이도 D도 같은 Glicko-2 척도의 레이팅으로 관리한다.

1.  **앵커 세트:** STEP 0에서 영역별 기준 문제 세트를 정하고 D=1500으로 고정한다.
2.  **초기 추정:** 생성 파라미터(블록 수, 탐색 깊이, 시간 압박, 정답 경로 수 등)를 D로 바꾸는 변환 함수를 영역별로 정의한다.
3.  **자동 보정:** 사이클이 끝날 때 사용자 레이팅과 함께 그 문제가 속한 **생성 파라미터 구간의 레이팅(D ± RD)**도 갱신한다. 구간 레이팅은 RD 하한을 두어 천천히 움직이게 하고, 정책 테이블에 버전과 함께 저장한다.

**문제 시도 판정:** `S=1`은 보조 수단 없이 성공, `S=0`은 유효한 실패. 힌트·되감기 사용과 기술적 무효는 갱신하지 않는다.

**출제 난이도:** Glicko-2 기대값으로 정답 확률이 75%가 되는 D를 역산해 출제한다(RD가 작을 때 약 `R − 191`). 여기에 난이도 편차를 섞어 단조로움을 막는다.

## 6.3 TETR.IO 실전 기록 앵커

실전 MMR이 실제 TETRA LEAGUE 실력과 같은 눈금이 되도록, 사용자의 실제 기록을 기준점으로 쓴다.

-   **입력:** 최초 설정과 UI-09에서 TETR.IO 프로필의 TETRA LEAGUE **Glicko ± RD**를 직접 입력할 수 있다(오프라인 수동 입력, 선택 사항).
-   **초기값:** 입력하면 `matchRating`을 그 Glicko로 시작하고, RD는 입력값과 150 중 큰 값으로 둔다. 입력하지 않으면 1500 ± 350.
-   **봇 눈금 맞추기:** 앵커가 있으면 평가전 결과로 AI 프리셋 등급 전체의 오프셋을 추정해, 봇 등급을 사용자의 TL Glicko 눈금에 맞춘다.
-   **재보정:** 사용자가 새 TL 기록을 입력할 때마다 앱 점수와의 차이를 기록하고 오프셋을 다시 계산한다. 입력 이력은 모두 보존한다.
-   **표시:** 앱 실전 MMR은 "TL Glicko 환산 추정치(± 범위)"로 표시한다. TR과 랭크 문자(S, X 등)는 TETR.IO 전체 이용자 분포에 따라 정해지므로 앱에서 계산·표시하지 않는다.

## 6.4 진단과 독립 실력 측정

-   **최초 진단:** 기술별 기본 문제 + 선택 오프너 실행 과제. 건너뛰면 일반 훈련에서 보정한다.
-   **독립 실력 측정:** 3세트마다 한 번 제안하며 사용자가 언제든 실행할 수 있다. 같은 구성·난이도·시간 기준의 미출제 검증 문제를 쓰고, 사이클 카운트·가중치와 분리해 이전 측정과 비교한다.

## 6.5 가중치 스케줄러

1.  활성 영역과 하위 태그의 최근 성과를 조회한다.
2.  최근 실패·지연이 큰 기술에 가중치를 더한다(초기 범위 0.8~1.8배). 숙련 기술도 최소 비중을 유지한다.
3.  12문제 안에서 한 영역 최대 5문제, 서로 다른 영역 최소 3개(초기값).
4.  영역을 고른 뒤 **그 영역의 기술 MMR**에 맞춰 난이도를 정한다.
5.  재도전·힌트 다시 보기는 문제 수를 늘리지 않는다.

**오프너 영역 내부 비율(초기값):** 주력 분기 실행 70% / 주력 불가 판정·전환(예외 또는 자유 스태킹으로 넘어가는 판단) 20% / 예외 분기 실행 10%. 전체 12문제가 아니라 오프너 문제 안에서의 비율이다.

# 7. 3사이클 운영과 AI 스파링

## 7.1 사이클 상태 머신

`DIAGNOSIS → TRAINING_1(12) → MINI_1 → TRAINING_2(12) → MINI_2 → TRAINING_3(12) → EVALUATION_BO3 → RESULT → TRAINING_1`

-   문제는 성공/실패가 확정되면 1개로 센다. 재도전은 추가로 세지 않는다.
-   미니 대결은 단판이며 건너뛰거나 미룰 수 있다.
-   평가전은 미룰 수 있고, '평가 없이 종료'를 고르면 실전 MMR은 그대로 두고 세트를 닫는다.
-   경기 진행은 라운드 경계에서 저장·재개한다.

## 7.2 AI 경기 규칙

-   AI는 **합법 수 생성 + 필드 평가 탐색 + 실제 입력 실행**을 하는 오프라인 봇이다. 사용자가 볼 수 없는 정보(Next 5개 이후 블록, 상대 난수)는 AI에게도 주지 않는다.
-   난이도는 PPS, 입력 지연, 탐색 깊이, 공격 효율, 다운스태킹, 안전 성향으로 조절한다.
-   **상대 선택:** 사용자 `matchRating ± RD`와 각 프리셋 `botRating ± RD`로 Glicko-2 예상 승률을 계산해, **예상 승률 40~60% 안에서 50%에 가장 가까운 프리셋**을 고른다. 해당 프리셋이 없으면 가장 가까운 것을 쓰고 기록에 표시한다.
-   라운드는 TETRA LEAGUE와 같이 한쪽이 패배할 때까지 진행한다(Top Out, 시간 경과에 따른 공격 배율 변화). 라운드 시간 제한과 무승부는 없다.
-   평가전은 TETRA LEAGUE 경기 방식(선착 승리)을 축약한 BO3다. 먼저 2승한 쪽이 이기며, 세트 무승부는 없다.

## 7.3 AI 프리셋 보정 절차

1.  **기준 봇:** 프리셋 하나를 기준 봇으로 정하고 `botRating=1500`으로 고정한다. 6.3의 TL 앵커가 있으면 이 눈금 전체를 앵커 기준으로 옮긴다.
2.  **봇 리그전:** 인접 프리셋끼리 쌍마다 최소 200판을 치러 Glicko-2로 `botRating ± RD`를 산출하고, 신뢰 구간과 함께 보정 보고서에 기록한다.
3.  **단조성 확인:** 프리셋 등급이 PPS·탐색 깊이 순서와 일관되게 오르는지 확인한다.
4.  **사용 중 보정:** 사용자 평가전 결과로 프리셋 등급을 조정하되, 프리셋 RD 하한을 두어 천천히 움직이게 하고 `calibrationVersion`을 올린다.

경기 기록에는 `botPresetId`, `calibrationVersion`, `botRating`을 저장한다.

## 7.4 실전 점수와 결과 분석

-   **미니 대결:** 실전 MMR은 바뀌지 않는다. 입력·공격·방어·스핀·PC 기회·오프너 성공/전환 등 엔진으로 관측한 기록을 다음 사이클 가중치에 반영한다.
-   **평가전:** 각 라운드를 한 경기(승=1, 패=0)로 보고, 세트가 끝나면 그 라운드들을 한 레이팅 기간으로 묶어 상대 봇의 `botRating ± RD`와 함께 Glicko-2로 갱신한다.
-   약점은 엔진 이벤트로 확인된 것만 하위 기술 가중치에 연결한다. 패배 자체를 특정 기술 약점으로 해석하지 않는다.

# 8. 오프너 시스템: 주력 1개 + 예외 1개

## 8.1 선택 원칙

-   사용자가 **주력(`primary`) 1개와 예외(`fallback`) 1개**를 직접 고른다. 두 항목은 서로 달라야 한다.
-   예외는 두 번째 암기형 오프너이거나 검증된 **자유 스태킹 전환 템플릿**일 수 있다. 템플릿도 고유 `openerId`와 판정 규칙을 가진다. 주력은 암기형 오프너만 고를 수 있다.
-   실행 순서: 보이는 블록 정보로 주력이 가능하면 주력 → 주력이 불가·불리로 확정되면 예외 → 둘 다 아니면 자유 스태킹.
-   평가 기준은 고집이 아니라 **선택의 타당성, 안정적 실행, 후속 전개**다.

## 8.2 실행 가능성 표시

'100% 가능'은 정의된 룰셋·정보 조건·Bag 범위의 모든 경우에 실행 경로가 존재함을 검증한 경우에만 표시하고, **검증 범위를 함께 표시**한다.

-   `fullSequenceFeasible`: 전체 순서를 알 때의 경로 존재 여부(오프라인 검증용)
-   `visibleInfoFeasible`: 공개된 Next/Hold만으로 안전한 분기가 있는지(실전 판정용)
-   `coverageEstimate`: 표본 기준 실행 가능 비율과 신뢰 구간
-   `abandonRule`: 주력 포기·예외 전환·자유 스태킹 허용 조건

실전 판단은 그 시점에 공개된 정보 기준으로만 채점한다.

## 8.3 라이브러리 구조

오프너는 유효 분기를 잇는 그래프(상태·배치·조건)로 저장한다.

-   `OpenerDefinition`: id, 이름, 룰셋 버전, 요구 능력 벡터, 분기 그래프 버전
-   `OpenerBranch`: 시작 보드·Next/Hold 조건, 합법 배치, 다음 분기, 종료·전환 상태
-   `OpenerCoverage`: 검증 범위, 가능 비율, 조건, 증명 경로
-   `OpenerProfile`: 숙련 MMR ± RD, 분기 성공률, 속도·실수·실전 기록

**초기 라이브러리:** TKI, DT Cannon, PCO, 자유 스태킹 전환 템플릿. 수록 분기 범위는 STEP 0에서 확정한다. 각 오프너의 공격 잠재력·후속 전개 값은 TL-S2 공격표(B2B 차징·Surge·PC 공격량 포함)와 오프너 페이즈를 적용해 산출한다.

## 8.4 학습 단계

1.  **동작 자동화:** 같은·비슷한 조건 반복으로 정확도와 속도 향상
2.  **분기 적응:** 다양한 Bag 순서에서 올바른 분기 선택
3.  **후속 전개:** 오프너 종료 후 공격·스태킹·B2B 연결
4.  **전환 판단:** 주력이 불가·위험할 때 예외 또는 자유 스태킹
5.  **실전 적용:** AI 대결에서 강제 없이 사용률·성공률·이탈 판단 평가

# 9. 1회 오프너 추천

## 9.1 트리거

정상 완료된 BO3 평가전 중 **아래 최소 데이터 조건을 처음 충족한 평가전**이 끝난 직후, 사용자별 자동 추천 이벤트를 **딱 한 번** 생성한다.

-   오프너 영역 유효 시도 10회 이상
-   오프너 관측이 있는 실전 라운드(미니 포함) 4회 이상

조건을 채우기 전의 평가전은 추천을 만들지 않는다. 미루기·평가 없이 종료·기술적 무효·중도 종료된 평가전은 트리거가 아니다. 이벤트가 생긴 뒤에는 자동 추천이 다시 나오지 않으며, 재분석은 UI-07에서 사용자가 직접 실행할 때만 한다.

## 9.2 분석 입력과 적합도

-   **사용자 벡터:** PPS, 피네스 오류율, 스핀·PC 실행, Hold/Next 판단, 공격 효율, 복구 안정성, 분기 적응, 오프너 성공/전환 기록
-   **오프너 벡터:** 실행 가능 범위, 조작 복잡도, 분기 암기 부담, 공격 잠재력, 지형 안정성, 후속 전개, 학습 비용

**조합 적합도(100점, 초기값):** 능력-요구 적합 35, 현재 관측 성과 25, 주력+예외 상호 보완 20, 공격·후속 잠재력 10, 학습 부담 10. 단순 평균이 아니라 *주력이 커버하는 상황 + 주력 불가 시 예외가 보완하는 상황*을 조합 단위로 평가한다.

-   적합도는 점수와 함께 **80% 신뢰 구간**을 계산한다(관측 데이터의 RD와 모델 추정 불확실성을 합산).
-   변경 추천 조건: ① 추천 조합이 현재 조합보다 **8점 이상 높고**, ② **추천 조합 구간의 하한이 현재 조합 구간의 상한보다 높을 때**. 둘 중 하나라도 아니면 유지를 권한다(`NO_CHANGE`).
-   관측하지 않은 오프너의 수행 수준은 "모델 추정값"으로 구분해 표시한다.

## 9.3 상태 머신

`PENDING → ANALYZING → READY → APPLIED / DECLINED / DEFERRED`, `ANALYZING → NO_CHANGE / UNAVAILABLE`, `DEFERRED → APPLIED / DECLINED`

| 상태 | 의미 |
|-------|---------------------|
| `APPLIED` | 사용자가 2단계 확인 후 새 조합 적용 |
| `DECLINED` | 사용자가 현재 조합 유지 |
| `NO_CHANGE` | 엔진이 현재 조합 유지를 권함 |
| `DEFERRED` | 나중에 결정. 자동 팝업 없이 UI-07에서 열기 |
| `UNAVAILABLE` | 검증 부족. 자동 재추천 없이 수동 재분석 가능 |

`firstRecommendationEventId`에 사용자별 유일성 제약을 둔다.

## 9.4 승인과 적용

1.  현재 조합과 추천 조합의 적합도·신뢰도·근거를 나란히 보여준다.
2.  **추천 적용 / 현재 유지 / 나중에 결정** 버튼을 제공한다.
3.  '추천 적용'은 변경 전후 비교와 '기존 숙련도 보존' 안내 화면으로 이어지고, 여기서 **변경 확정**을 눌러야 적용된다.
4.  확정 시 하나의 DB 트랜잭션으로 처리: 설정 버전 확인 → 조합 유효성 → 변경 이력 기록 → `OpenerLoadout` 갱신 → `APPLIED` 저장.
5.  실패·충돌·종료 시 기존 조합이 유지되고 재승인을 받는다. 중복 요청은 이벤트 ID로 멱등 처리한다.

## 9.5 기록 보존

-   `OpenerProfile(openerId)`와 `OpenerLoadout(primaryId, fallbackId)`를 분리 저장한다. 조합을 바꿔도 모든 오프너의 MMR·분기 숙련도·경기 기록은 그대로 남는다.
-   `OpenerHistory`는 당시 역할(`roleAtTime`)을 보존한다.
-   수동 변경과 이전 조합 복원은 언제든 가능하다.
-   오래 쓰지 않은 오프너는 RD만 늘리고 점수는 유지한다.

## 10.3 데이터 불변식

-   `primaryOpenerId ≠ fallbackOpenerId`, 두 ID 모두 활성 룰셋에서 유효
-   로드아웃 변경은 어떤 `OpenerProfile` 점수도 직접 수정하지 않는다
-   자동 추천 이벤트는 사용자당 최대 1개
-   기술 MMR은 유효 시도에서만, 실전 MMR은 완료된 평가전에서만 변경
-   모든 문제·경기 기록은 당시의 `rulesetVersion / generatorVersion / calibrationVersion`과 연결

| 상황 | 기본 동작 |
|----------------|------------------------------|
| 문제 생성·탐색 실패 | 검증 캐시로 대체, 없으면 다른 영역 출제 |
| 문제 중간 종료 | 마지막 체크포인트에서 재개, 미제출 문제는 세지 않음 |

| 미니 대결 건너뛰기 | `skipped=true`, 승패·MMR 없이 다음 사이클 진행 |
| 평가전 연기 | 진행도 저장, 추천 판단 보류 |

| 추천 시점 근거 부족 | `UNAVAILABLE` 또는 유지 권고 |
| 추천 후 사용자가 수동 변경 | `sourceLoadoutVersion` 충돌 감지, 새 승인 필요 |
| 승인 중 종료·저장 실패 | 원자적 롤백, 기존 조합·숙련도 유지 |
| 적용 버튼 중복 클릭 | 이벤트 ID로 멱등 처리, 변경 1회 |
| 이후 평가전 완료 | 자동 추천 없음 |

## 12.3 작업 규칙

-   **결정 기록:** 문서에 없는 선택은 스스로 정하고 `docs/DECISIONS.md`에 "결정 · 이유 · 대안 · 되돌리는 방법"으로 남긴다.
-   **룰셋 출처:** TL-S2 수치는 공개 자료(TETR.IO 메커니즘 FAQ, 공식 패치 노트, TETR.IO 위키 등)에서 가져오고, 값마다 출처와 확인 상태(`verified` / `unverified`)를 `docs/RULESET_SOURCES.md`와 `rulesets/TL-S2.toml`에 기록한다. 확인되지 않은 값도 설정으로 분리해 나중에 바꿀 수 있게 만든다. 시간 경과에 따른 공격 배율 증가처럼 존재 여부가 불확실한 규칙도 켜고 끌 수 있게 구현한다.
-   **오픈소스:** MIT·BSD·Apache 2.0·MPL 2.0 라이선스 코드는 써도 된다. GPL 계열은 쓰지 않는다. 사용한 라이선스는 `THIRD_PARTY_LICENSES.md`에 정리한다. 다른 언어로 된 프로젝트(예: solution-finder)는 알고리즘만 참고한다.
-   **명칭:** 제품명·UI·설치 파일에 "Tetris" 등 타사 상표와 로고를 쓰지 않고 '테트로미노' 같은 일반 용어를 쓴다.
